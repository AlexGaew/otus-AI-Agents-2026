# write-tests

Процедура написания юнит-тестов в рамках TDD (см. правило `.claude/rules/tdd.md`).

## Шаги

1. Определи поведение одной фразой: что должно происходить при каком входе. Если требование неоднозначно, сверься с `ТЗ-telegram-bot.md` и спроси пользователя.
2. Найди существующие тесты рядом с изменяемым кодом и повтори их стиль и структуру.
3. Напиши один тест на одно поведение в схеме given / when / then. Имя теста описывает поведение, а не метод.
4. Запусти тест (команда в `AGENTS.md`, раздел «Команды») и убедись, что он падает по ожидаемой причине, а не из-за ошибки компиляции или настройки.
5. Остальные тесты пиши по одному, повторяя шаги 3–4 для каждого.

## Что покрывать

- Основной сценарий и граничные случаи: пустой текст, очень длинный текст, ссылка без заголовка, повтор одной и той же ссылки.
- Отказ пользователю не из белого списка: бот не отвечает и ничего не сохраняет.
- Сбой внешних сервисов: LLM недоступна или вернула мусор, страница по ссылке не открылась. Запись при этом должна сохраниться без тегов.

## Чего не делать

- Не ходить в реальный Telegram, в реальную LLM и в сеть: внешние клиенты подменяй заглушками.
- Не подключать реальную PostgreSQL в юнит-тестах; для проверки запросов к БД нужен отдельный интеграционный тест.
- Не проверять детали реализации (порядок вызовов, приватные методы), только наблюдаемое поведение.
